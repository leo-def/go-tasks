## 🛠 Recommended Skills

### Skill 1: New Module Implementation
**When**: Adding a feature that requires a new domain module
**Process**:
1. Review SPEC.md module registry (doesn't your module already exist?)
2. Create 5 files in `internal/{moduleName}/`: model, repository, service, handler, module
3. Define GORM model with appropriate tags
4. Implement repository interface with CRUD + domain queries
5. Implement service interface with business logic
6. Implement handler with HTTP endpoints
7. Register module in main.go
8. Write tests for each component
9. Run migrations if new tables needed

**Example**: Adding a "Document" module for file storage

### Skill 2: Endpoint Development
**When**: Adding new HTTP endpoints to existing module
**Process**:
1. Add handler method: `func (h *ModuleHandler) Action(c *gin.Context) { }`
2. Register route: `router.METHOD("/path/:id", h.Handler.Action)`
3. Extract params/body from Gin context
4. Call service method
5. Map result to HTTP response
6. Test with curl or Postman

**Example**: Adding PUT /api/v1/users/:id endpoint

### Skill 3: Database Query Optimization
**When**: Performance issues or complex queries needed
**Process**:
1. Understand current GORM query
2. Use Explain() to see execution plan
3. Add indexes if needed
4. Use eager loading (Preload) to avoid N+1
5. Test performance improvement
6. Add migration if schema change needed

**Example**: Optimizing ListUserTasks query

### Skill 4: Error Handling & Validation
**When**: Adding validation or improving error messages
**Process**:
1. Add validation at handler boundary
2. Create custom error type if needed
3. Map errors to HTTP status codes
4. Ensure error messages are informative
5. Test error cases in unit tests

**Example**: Validating email format, handling duplicate key errors

## 🧠 Project-Specific Knowledge

### Core Concepts

**Module Pattern**
Each domain (user, task, company, etc.) has:
- `Model`: GORM struct with database mapping
- `Repository`: Database operations interface + implementation
- `Service`: Business logic layer
- `Handler`: HTTP request/response handlers
- `Module`: Initialization and dependency wiring

**Dependency Injection**
- No global state (no global DB, logger, etc.)
- Dependencies injected through function parameters
- Constructor functions (`New{Type}`) return fully initialized objects
- Enables testing with mocks

**GORM Patterns**
- Models are structs with `gorm` tags
- Query: `db.Where().First()`, `db.Find()`, `db.Create()`, `db.Updates()`, `db.Delete()`
- Relationships: `Preload()` for eager loading, `Association()` for managing
- Hooks: `BeforeSave`, `AfterFind` for model logic

**Error Handling**
- All functions return error as last value
- Wrap errors with context: `fmt.Errorf("operation failed: %w", err)`
- Map to HTTP status: 400/validation, 404/not found, 500/internal
- Never return raw database errors to HTTP layer

### Common Patterns in This Project

**Creating a Repository**
```go
type UserRepository interface {
    FindByID(ctx context.Context, id uint) (*User, error)
    Create(ctx context.Context, user *User) error
}

type userRepositoryImpl struct {
    db *gorm.DB
}

func (r *userRepositoryImpl) FindByID(ctx context.Context, id uint) (*User, error) {
    var user User
    if err := r.db.WithContext(ctx).First(&user, id).Error; err != nil {
        return nil, fmt.Errorf("user not found: %w", err)
    }
    return &user, nil
}

func NewUserRepository(db *gorm.DB) UserRepository {
    return &userRepositoryImpl{db}
}
```

**Creating a Service**
```go
type UserService struct {
    repo UserRepository
}

func (s *UserService) GetUser(ctx context.Context, id uint) (*User, error) {
    return s.repo.FindByID(ctx, id)
}

func NewUserService(repo UserRepository) *UserService {
    return &UserService{repo}
}
```

**Creating a Handler**
```go
type UserHandler struct {
    service UserService
}

func (h *UserHandler) GetUser(c *gin.Context) {
    id := c.Param("id")
    // Parse id, validate
    user, err := h.service.GetUser(c.Request.Context(), parsedID)
    if err != nil {
        c.JSON(404, gin.H{"error": "not found"})
        return
    }
    c.JSON(200, user)
}

func NewUserHandler(service UserService) *UserHandler {
    return &UserHandler{service}
}
```

### Known Gotchas

1. **GORM Query vs Scan**
   - ✅ `db.First()` for single row, `db.Find()` for multiple
   - ❌ Don't forget `.Error` to check for errors: `if err := db.First(&user).Error; err != nil`

2. **Context Cancellation**
   - ✅ Always pass context through: `db.WithContext(ctx).First()`
   - ❌ Ignoring context can lead to hanging queries

3. **N+1 Query Problem**
   - ✅ Use `Preload()` for relationships: `db.Preload("Tasks").First()`
   - ❌ Looping and querying individually

4. **Validation Errors vs Database Errors**
   - ✅ Validation at handler boundary (400 status)
   - ✅ Database errors returned by repository (500 status)
   - ❌ Don't mix them

5. **Gin Context Lifecycle**
   - ✅ Gin context valid only during request handling
   - ❌ Don't store Gin context globally
   - ✅ Use request.Context() for background operations

## 🔄 Workflow: Adding a New Feature

### Example: Add "Priority" to Tasks

1. **Add Column to Database**
   - Create migration: `make migrate-create name=add_priority_to_tasks`
   - Write migration SQL

2. **Update Model**
   - Add `Priority int` field to Task struct with `gorm` tag

3. **Update Repository**
   - Add query methods if needed (e.g., `FindByPriority`)

4. **Update Service**
   - Add business logic for priority handling

5. **Update Handler**
   - Add fields to request struct
   - Add endpoint if needed

6. **Write Tests**
   - Test repository queries
   - Test service logic
   - Test handler endpoints

7. **Run Locally**
   - `make dev` or `make debug`
   - Test with curl or Postman

Before accepting AI-generated code:
- [ ] Follows 5-file module pattern
- [ ] No global state used
- [ ] Errors wrapped with context
- [ ] No circular dependencies
- [ ] Repository, service, handler properly separated
- [ ] Tests included for new code
- [ ] No Gin context leaked into service/repository
- [ ] GORM `.Error` checked on queries
- [ ] Context passed through to database calls
- [ ] Matches existing code style and patterns

## 🚨 Restrictions & Boundaries

### ❌ Forbidden Without Manual Review
- Changing module structure (breaking pattern)
- Database schema changes without migration
- Breaking API contracts (changing endpoint paths/methods)
- Introducing dependencies (importing external packages)

### ⚠️ Requires Testing
- Query optimization
- Concurrency/goroutine code
- Error recovery logic
- Transaction handling

### ✅ Safe to Implement
- New modules following pattern
- New endpoints with existing models
- Service business logic
- Test additions
- Documentation improvements
